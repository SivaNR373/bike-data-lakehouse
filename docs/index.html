Executive Summary

The Bike Data Lakehouse is a hands-on batch Data Engineering project that ingests six CSV datasets from CRM and ERP source systems, stores them as Bronze Delta tables, applies cleansing and cross-system validation in Silver, and produces an analytics-ready Gold dimensional model.

Bronze Write Pattern

df.write.format("delta") \
    .mode("overwrite") \
    .saveAsTable("bike_lakehouse.bronze.crm_cust_info")
Engineering decision: source column names were preserved in Bronze. When the explicit schema initially used cst_gender instead of the actual source column cst_gndr, Delta metadata validation caught the mismatch. The schema was corrected to match the source rather than enabling schema merging.

Key Engineering Challenges Solved

1. Delta Metadata Mismatch

Explicit schema hardening exposed a mismatch between the existing Bronze table's cst_gndr column and an initially defined cst_gender field. The solution was to correct the explicit schema to match the raw source contract rather than using mergeSchema.

2. Sales Date Parsing

Source sales dates were integer values in yyyyMMdd form. Normal date conversion did not safely handle invalid values such as 0 and 32154, so tolerant date parsing was used. The final Silver table retained 19 null order dates corresponding to invalid source values.

3. Customer Deduplication

The CRM customer source contained duplicate customer IDs/keys. The Silver transformation removed null customer IDs and selected the most complete/latest appropriate record instead of arbitrarily dropping duplicates.

4. Cross-System Identifier Reconciliation

CRM and ERP systems used different customer and product identifier formats. The pipeline normalized the relevant identifier structures so customer and product relationships could be validated across systems.

5. Historical Product Versions

Product keys appeared across multiple product versions. The Gold product dimension therefore retained the historical rows, while the sales fact kept its business keys instead of joining to a potentially multiplying historical dimension row.

6. Git Synchronization During Development

During repository synchronization, local Bronze changes were preserved while bringing the Databricks Git workspace up to date.

Next Steps & Future Enhancements

The current implementation intentionally focuses on a clean, complete batch Medallion pipeline. The following items are future V2 hardening opportunities rather than features claimed as implemented today.

Incremental Processing
Move beyond full overwrite ingestion toward incremental/CDC patterns where source behavior supports them.
Audit Metadata
Add ingestion timestamps, batch/run identifiers and operational metadata.
Operational Framework
Reusable ingestion framework, parameterization, structured logging, retries and alerting.
Testing
Automated data-quality tests and regression checks for pipeline deployments.
CI/CD
Formal deployment workflow around Git-based development and Databricks assets.
Performance
Optimize partitioning, file sizes, joins and Spark execution as data volume grows.
Monitoring
Job-level monitoring, failure alerts and operational dashboards.
Streaming
Extend the batch foundation into a separate real-time/streaming implementation as a future project.
Scope note: Incremental loading, audit columns, production monitoring, CI/CD automation, and streaming are not presented as implemented features of this current project.
